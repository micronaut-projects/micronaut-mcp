3 Breaking Changes

This section documents breaking changes between Micronaut MCP versions.

2.2.0

  • The STDIO server now accepts up to 16,777,216 UTF-16 code units per inbound JSON-RPC line, excluding the line terminator. A longer line ends the stdio session without a JSON-RPC error response. Clients that send large tool arguments must keep the entire serialized request within this limit.

  • With the HTTP transport, the requests and notifications handed to the SDK carry their parameters as parsed JSON: McpSchema.JSONRPCRequest.params() and McpSchema.JSONRPCNotification.params() are now an io.micronaut.json.tree.JsonNode (an object or an array) instead of a Map. They are still a Map (or a List) when the application replaces the McpJsonMapper bean, even with a mapper that delegates to the Micronaut one. The SDK handlers convert the parameters with the McpJsonMapper, so this only affects code that replaces or decorates the McpStatelessServerHandler bean and reads params() directly. Such code can convert the parameters with the McpJsonMapper bean, which accepts both forms: mcpJsonMapper.convertValue(request.params(), new TypeRef<Map<String, Object>>() { }).

  • With the HTTP transport, a message that is not a valid JSON-RPC 2.0 request or notification gets HTTP 400 with the JSON-RPC error -32600 (Invalid Request), a null id and a message that names the problem. Before, such a message either got HTTP 500 or reached the SDK. This includes a jsonrpc member that is missing or other than "2.0", a method that is missing or not a string, an id that is null, a boolean, a fractional number or larger than a 64-bit integer, params that are neither an object nor an array, and a batch (an array of messages).

  • With the HTTP transport, an exception other than an McpError that the SDK throws outside your tools, prompts, resources and completions, for example while it converts the request parameters, is logged at ERROR and answered with the JSON-RPC error -32603 and the message Internal error, without the message of the exception. An exception other than an McpError thrown by your prompts, resources and completions is also answered with -32603 and the message Internal error, and logged at WARN with its stack trace, unless an McpErrorExceptionMapper maps it: map the exceptions whose message the client may see. Tools report their failures as tool execution errors instead, see below. A notification whose handling fails is answered with the HTTP status of the error and no body, because a JSON-RPC error response needs an id.

  • A @ToolArg parameter is always a named property of the input schema of a tool, even when its type has a @JsonSchema. Only a parameter without @ToolArg can provide the schema of the whole input.

  • The $id of generated JSON schemas, which clients see in tools/list, defaults to classpath:META-INF/schemas/<name> with Micronaut JSON Schema 2.3.2 and later, instead of http://localhost:8080/schemas/<name>;. Set the micronaut.jsonschema.baseUri annotation processor option to choose another base.

  • A tool method that throws an unmapped exception now returns a result with isError set to true and a generic message identifying the tool. Argument binding and bean validation failures return isError with a message describing the invalid input. With the HTTP transport the response status is 200 instead of 400 or 500. In particular, a bean validation failure of a tool argument is no longer the error -32602. Existing McpErrorExceptionMapper beans still produce JSON-RPC errors for the exceptions they map. To answer with a JSON-RPC error, throw an io.modelcontextprotocol.spec.McpError, or map an exception that Micronaut MCP does not map itself with an McpErrorExceptionMapper. Clients that detect a failed call by the error member of the JSON-RPC response must also check isError in its result. Likewise, access logs, firewall rules and alerts that count 4xx responses no longer see tool arguments that fail validation, which are logged at DEBUG level. See Tool Errors.

  • A tool failure that no McpErrorExceptionMapper maps is logged by the io.micronaut.mcp.server.registry.ToolRegistry logger at WARN level. The registry renders the exception and its stack trace on one log line. A tool that fails often for expected reasons, such as an unknown identifier, should return a CallToolResult whose isError is true instead of throwing, which is not logged. See Tool Errors.

  • The message of a structured content or tool input that does not match its JSON schema lists the schema errors, separated by semicolons, after the prefix the SDK adds, for example Tool (moon-phase-at-date) input validation failed: /date: does not match the date pattern must be a valid RFC 3339 full-date. It no longer contains Validation failed: structuredContent does not match tool outputSchema nor the ValidationMessageAdapter representation of the errors.

  • Every @ResourceTemplate declaration must now specify uriTemplate. Update any declarations that omit it before recompiling.

  • The values of resource template variables are now percent-decoded before they are bound. This is URI decoding: a + is no longer turned into a space, as URLDecoder.decode did. Remove any decoding of the values from your methods, or they are decoded twice: %2525 is bound as %25, which a second decoding turns into %. Values that used to arrive escaped can now contain control characters, such as a CR LF line break from %0D%0A, so methods that log or concatenate them must sanitize them. Malformed escapes, invalid UTF-8, and an encoded / (%2F) in a simple variable such as {path} yield an invalid params error. The same error applies when the SDK routes a URI to a template whose path it fails to match. To accept an encoded /, declare a reserved variable such as {+path}. See Resource Template Variable Decoding.

  • The HTTP endpoint now validates the Origin and MCP-Protocol-Version request headers, as the MCP specification requires. A browser-based client whose origin is neither a loopback origin nor listed in micronaut.mcp.server.transport-security.allowed-origins now gets 403 Forbidden; add its origin to the list (and enable CORS for it). A request with an MCP-Protocol-Version header naming a version the server does not support (it supports 2025-03-26, 2025-06-18 and 2025-11-25) now gets 400 Bad Request. See Transport Security.

  • With the HTTP transport, the server advertises listChanged and subscribe as false. This overrides the list-changed and subscribe properties and any BeanCreatedEventListener of McpSchema.ServerCapabilities.Builder, because the server cannot send notifications outside the response to a request.

  • A server with list-changed set to true for tools, prompts or resources advertises that capability even when it has none of them, so they can be added at runtime. Clients may then list them and get an empty list. Set list-changed to false if your clients should not see an empty capability.

  • The LangChain4j MCP client connects to every connection of micronaut.mcp.client.http and micronaut.mcp.client.stdio together. micronaut.mcp.client.transport is deprecated and no longer selects the transport: with STDIO, the HTTP connections, including the embeddedServer connection of an application that is itself an HTTP MCP server, are no longer left out, so their tools reach the McpToolProvider. Remove the HTTP connections you do not want, and leave out the tools of embeddedServer with an McpToolFilter. See LangChain4j MCP Client.

  • The McpToolProvider of the LangChain4j client skips the servers that cannot be reached instead of failing, and connects to each server when its client is first used rather than when the provider is created. While one request creates the client of a connection, the other requests get no tools from that server instead of waiting.

  • With Micronaut Management, the new mcp health indicator of the LangChain4j client is down when any server cannot be reached, so /health and /health/readiness answer 503. Disable it with endpoints.health.mcp.enabled=false.

  • The LangChain4j StdioMcpTransport and StreamableHttpMcpTransport beans are prototypes owned and closed by their client, instead of singletons. Inject the McpClient of a connection rather than its transport.

  • The application fails to start when two MCP client connections have the same name, when an HTTP connection has no url, or when a STDIO connection has no command.

  • The Java SDK clients connect to their server when the bean is created, so injecting a client of a server that cannot be reached throws a BeanInstantiationException, which can fail the startup of the application. Inject a jakarta.inject.Provider or a BeanProvider of the client to connect when it is first used.

  • A connection has either a synchronous or an asynchronous Java SDK client: creating the second one fails. Declare a connection for each if the application needs both.

4.3.1 Transport

The protocol currently defines two standard transport mechanisms for client-server communication: stdio (communication over standard in and standard out) and Streamable HTTP

For stdio transport, define the property micronaut.mcp.server.transport as STDIO.

For HTTP transport, define the property micronaut.mcp.server.transport as HTTP.

Server to Client communication via an SSE stream is not yet supported. The server responses are currently only of Content-Type: application/json.

4.3.4 Server Capabilities

The injectable McpSchema.ServerCapabilities bean exposes the capabilities configured through your primitive beans and the list-changed and subscribe properties. You can customize these capabilities with a BeanCreatedEventListener for McpSchema.ServerCapabilities.Builder.

To read the capabilities clients receive in the initialize response, call getServerCapabilities() on the active SDK server bean. For example, with HTTP and micronaut.mcp.server.tools.list-changed=true, the injectable capabilities bean reports tools.listChanged as true and the server advertises it as false.

The HTTP server turns off listChanged and subscribe because it can send notifications only during a request. A BeanCreatedEventListener that replaces the capabilities on the server specification itself can override these flags, but clients would then wait for notifications that never arrive. See Adding and Removing Primitives at Runtime.

4.4 STDIO Transport

If you use Standard Input/Output (stdio) protocol, your server MUST NOT write anything to its stdout.

Disable the Micronaut banner and configure Logback not to log to stdout.

For example, you can configure Logback to log to a file or to stderr (see <target>System.err</target> in the configuration file below):

<configuration>
    <appender name="STDERR" class="ch.qos.logback.core.ConsoleAppender">
        <target>System.err</target>
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="STDERR" />
    </root>
</configuration>

4.6 MCP Transport Context

Micronaut MCP ships MicronautMcpTransportContext, an extension to io.modelcontextprotocol.common.McpTransportContext, which allows you to access concepts such as the authenticated user, locale, host, etc.

With the HTTP transport, the context reads its values from the HTTP request the first time they are asked for, and it keeps the request reachable for as long as the context is reachable. Do not keep the context after the request is handled, for example in a cache or a background task: copy the values you need instead.

The host comes from the request headers (Forwarded, X-Forwarded-Host and Host by default), which the client can set. Do not use it for security decisions, such as building callback URLs or choosing a tenant, unless the host resolution is configured for your proxy, for example with micronaut.server.host-resolution.allowed-hosts.

4.7 MCP Request Context

Declare a parameter of type McpRequestContext in a tool, prompt, resource or completion method to report progress, send log messages to the client, check whether the client disconnected, or ask the client for information:

import io.micronaut.mcp.annotations.Tool;
import io.micronaut.mcp.server.context.McpRequestContext;
import io.modelcontextprotocol.spec.McpSchema;
import jakarta.inject.Singleton;

@Singleton
class CatalogTools {
    @Tool(description = "Imports the pages of the catalog")
    String importCatalog(int pages, McpRequestContext context) {
        for (int page = 1; page <= pages; page++) {
            importPage(page);
            context.progress(page, pages, "Imported page " + page); // (1)
        }
        context.log(McpSchema.LoggingLevel.INFO, "catalog", "Imported " + pages + " pages"); // (2)
        return "done";
    }
}

McpRequestContext is an interface, so a unit test that calls a primitive method directly can pass a mock or its own implementation.

Progress

progress sends a notification only when the client sent a progress token with the request, in _meta.progressToken; otherwise it does nothing. progressToken() returns the token, or null. Since every progress notification repeats it, the token must be a string of at most 256 characters or an integer, as the protocol allows; another token is ignored, as if the client had not asked for progress.

Log messages

log sends a log message to the client. When a primitive declares an McpRequestContext parameter, the server advertises the logging capability, since it may send log messages.

The STDIO server applies the level a client sets with logging/setLevel. The stateless HTTP server returns a JSON-RPC Method not found error for a valid logging/setLevel request because it cannot apply a threshold across requests.

Log messages are sent to the client, and usually reach the language model. They are not server logs: as the specification requires, do not put credentials, personal data, exception messages or internal details such as hosts, queries or file paths in them. Over HTTP, all levels are eligible for delivery, including debug.

The response over HTTP

Over the HTTP transport, the response stays JSON until the method sends its first notification. If the client accepts both application/json and text/event-stream, the response then becomes an event stream: each notification is sent as an event while the method runs, followed by the JSON-RPC response. A log message of any level, even debug, makes the response an event stream. For the example above, a client that sends:

POST /mcp
Content-Type: application/json
Accept: application/json, text/event-stream

{"jsonrpc": "2.0", "id": 1, "method": "tools/call",
 "params": {"name": "importCatalog", "arguments": {"pages": 2}, "_meta": {"progressToken": "import"}}}

receives a text/event-stream response with these events:

data: {"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"import","progress":1.0,"total":2.0,"message":"Imported page 1"}}

data: {"jsonrpc":"2.0","method":"notifications/progress","params":{"progressToken":"import","progress":2.0,"total":2.0,"message":"Imported page 2"}}

data: {"jsonrpc":"2.0","method":"notifications/message","params":{"level":"info","logger":"catalog","data":"Imported 2 pages"}}

data: {"jsonrpc":"2.0","id":1,"result":{"content":[{"type":"text","text":"done"}],"isError":false}}

A request that sends no notification is answered with JSON, and so is a client that only accepts JSON, whose notifications are dropped. On the blocking server, so that the response can become a stream while the method runs, a request for a primitive that declares an McpRequestContext, from a client that accepts both, runs the method on another thread of the blocking executor.

Once the response is an event stream, its HTTP status is 200 OK, even when the request fails: the error arrives as a JSON-RPC response with an error member in the last event. Check that member, not the HTTP status. A request that fails before its first notification is answered with JSON and the usual error status.

Only requests for a primitive that declares an McpRequestContext parameter may become an event stream. A client that accepts text/event-stream with a quality of 0 is answered with JSON. If a slow client lets more than 256 events, or notifications of more than about a million characters, pile up, further notifications are dropped, but the result is always sent.

Deploying a server that streams

An event stream stays open while the method runs, so the components between the client and the server must let it through as it is written:

  • The server sends no keep-alive while a method is silent. If the method pauses between notifications for longer than an idle timeout on the path, the connection is closed and the client never receives the result. Raise micronaut.server.idle-timeout, micronaut.server.read-idle-timeout, micronaut.server.write-idle-timeout and the read timeout of any reverse proxy or load balancer above the longest pause, or have a long-running method send a log message or progress regularly.

  • The event stream has the headers Cache-Control: no-cache, no-transform and X-Accel-Buffering: no, which nginx honours. Turn off response buffering for the MCP endpoint in any other reverse proxy, or the events arrive at once when the method returns, and a client that goes away is not noticed.

  • A request that fails after its first notification still has the HTTP status 200 OK, so access logs and proxy error rates do not count it; the server logs an unexpected error at the ERROR level.

  • A client that does not read keeps up to 256 notifications, of about a million characters at most, in memory for each request. Put a public endpoint behind authentication and a connection or rate limit.

Client disconnects

Once the HTTP response has become an event stream, isClientDisconnected() reports whether the server has observed the connection close. A disconnect stops event delivery. The primitive continues running and can finish any work already in progress. Over STDIO or with a plain JSON response the method returns false.

The supported MCP protocol revisions distinguish a transport disconnect from an explicit notifications/cancelled notification. This context does not handle protocol cancellation.

Elicitation and sampling

elicit and sample send requests to the client, which only the STDIO transport supports: over the stateless HTTP transport they throw UnsupportedOperationException.

They wait for the answer of the client. On a reactive STDIO server (micronaut.mcp.server.reactive set to true), a method without an executor runs on the thread that reads the messages of the client, which could then never read the answer, so elicit and sample fail there with an IllegalStateException. Annotate a method that calls them with @ExecuteOn(TaskExecutors.BLOCKING).

Primitives added at runtime through the MCP Java SDK server (see Adding Primitives at Runtime), and requests the SDK rejects before dispatching them, for example a call of an unknown tool, are not timed.

The timer is based on the OpenTelemetry semantic conventions for MCP, which are still in development, with these differences:

  • The conventions name the primitive with gen_ai.tool.name, gen_ai.prompt.name or the opt-in mcp.resource.uri, depending on the operation. The timer always uses mcp.primitive.name, a tag Micronaut MCP defines, not the conventions, because the Prometheus registry requires every timer of a name to have the same tag keys.

  • The conventions leave error.type out on success. The timer sets it to none, for the same reason.

  • The conventions do not count some JSON-RPC error codes as errors, for example -32602 (invalid params). The timer records every reserved code in error.type, so that a dashboard can tell them apart from successes.

  • The conventions time a request from when it is received until its response is sent. The timer covers only the method of the primitive: from when the server invokes it, including any wait for the executor of @ExecuteOn, until its result is mapped. The JSON-RPC parsing, the input validation of the SDK and the serialization of the response are not included.

With a meter registry that accepts different tag keys for one meter name, a Micrometer MeterFilter bean can map mcp.primitive.name to the attribute names of the conventions.

The timer publishes no histogram buckets by default, so Prometheus cannot compute percentiles such as the 95th. To publish them, register a MeterFilter bean whose configure method, for the meter named mcp.server.operation.duration, merges service level objectives into the distribution statistics, for example the bucket boundaries the conventions recommend: 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10, 30, 60, 120 and 300 seconds.

The timer is on by default whenever a MeterRegistry bean exists. Disable it with micronaut.mcp.server.metrics.enabled=false; your own observers still run. Disabling Micrometer itself with micronaut.metrics.enabled=false disables it too.

To observe operations, register a bean of type McpServerObserver. The server calls start() for each operation and calls stop() once on the returned observation. On a reactive server, start() runs on the subscribing thread, before any switch to the primitive’s @ExecuteOn executor. The thread delivering the result, completion, error or cancellation calls stop(). Keep per-operation state in the returned observation so it is available across threads. Either callback can run on an event loop and must return promptly.

The server logs observer failures and continues the operation. The interface is experimental and may change, for example to give observers the request context.

4.9 Security

Protect the HTTP endpoint of an MCP server against DNS rebinding attacks, and require clients to authenticate.

4.9.1 Transport Security

The HTTP endpoint validates two request headers, as the Streamable HTTP transport requires:

  • Origin, to prevent DNS rebinding attacks. A request whose Origin is not allowed is answered with 403 Forbidden. Requests without an Origin are allowed: browsers always send one, and other clients do not need one. Loopback origins (localhost, 127.0.0.1 and [::1], with http or https and any port) are allowed by default, so that local tools such as the MCP Inspector can connect. Other loopback forms, such as 127.0.0.2 or [::ffff:127.0.0.1], and other schemes, such as the capacitor://localhost of web view shells, are rejected unless listed. Allow the origins of browser-based clients with allowed-origins, or for any origin. Each entry is an origin, scheme://host[:port], without a path, as browsers send it; the default port of http and https can be left out. An entry that is not an origin, such as app.example.com, https://app.example.com/ui, https://app.example.com// or one with a port outside 1 to 65535, could never match, so it fails the startup. Wildcard subdomains, such as https://.example.com, are not supported. Clients that send Origin: null, such as file:// pages and sandboxed iframes, are rejected; only * allows them.

  • MCP-Protocol-Version. A request with a version the server does not support is answered with 400 Bad Request.

A request with more than one Origin header is answered with 403 Forbidden, and one with more than one MCP-Protocol-Version header with 400 Bad Request, so that a second value cannot pass for the one that is checked. The checks apply to every request routed to the MCP endpoint, whatever the shape of micronaut.mcp.server.endpoint and the context path; a request with a method the endpoint does not serve is answered with 405 Method Not Allowed.

The headers are checked by a filter on the MCP endpoint, before the request body is read. It runs after the CORS filter, so that a browser can read the rejection, and before authentication, so that a request from a foreign origin is answered with 403 rather than 401. Turn on DEBUG logging for io.micronaut.mcp.server.stateless to see why a request was rejected.

Validation is enabled by default, as the specification requires servers to validate the Origin header. It can be disabled with enabled: false (only the value false disables it), for example when a gateway in front of the server validates the Origin. Disabling it turns off both checks, including the MCP-Protocol-Version check, which gateways usually do not perform. The transport security properties are read at startup: changing them, for example through a refresh of the configuration, takes effect after a restart.

With the allowed hosts set, the resource is the canonical URL of the endpoint, the audience above.

4.10.1.4.3 Tool Annotation Method Return Type

In a method annotated with @Tool, you can use as a return type:

  • io.modelcontextprotocol.spec.McpSchema.CallToolResult

  • String

  • A class or Java record which will be serialized to JSON. If the return type is annotated with @JsonSchema and it is defined as the tool output it will be used as structured content.

Any of these can also be produced asynchronously, by returning a single value reactive type such as Mono<T>, a Publisher<T> that emits at most one value, or a CompletionStage<T>. Other reactive types, such as RxJava’s Single, are converted with the conversion service. The value it produces is used as if the method had returned it, and the result is chosen from that value rather than from the declared return type. A @JsonSchema type produced this way is still used as the structured output; producing no value is then a tool error.

A method returning a type that may emit several values, such as Flux<T>, fails the startup, unless it is annotated with @SingleResult. A Publisher<T> that emits more than one value fails the call.

The single-value rules also apply to methods annotated with @Prompt, @Resource, @ResourceTemplate, @PromptCompletion and @ResourceCompletion.

A @PromptCompletion or @ResourceCompletion method can also return a Flux<String> of suggestions. The response contains up to 100 suggestions in emission order. If the publisher emits a 101st suggestion, the server cancels the subscription, sets hasMore to true, and omits the unknown total.

How the methods are invoked depends on micronaut.mcp.server.reactive:

  • When it is false (the default), the HTTP endpoint handles requests on the blocking executor, which uses virtual threads where they are available. Methods run on that thread, can block, and see the current request through ServerRequestContext. The server waits for asynchronous return values. A method annotated with @ExecuteOn runs on the named executor, for example to limit how many calls run concurrently, and the request thread waits for the result. If you configure a fixed-size HTTP blocking executor, use a separate executor for asynchronous work that a request waits for, or enable the reactive server.

  • When it is true, methods run on the thread that received the request, which must not block. Annotate a method with @ExecuteOn to run it on another executor, for example @ExecuteOn(TaskExecutors.BLOCKING).

See Tool Errors for how a tool reports a failure.

  • If a tool throws an unmapped exception, the client receives a tool execution error with a generic message, such as Tool forecast failed. With a reactive server, a tool without @ExecuteOn can fail on the event loop. A synchronous appender writes the log on that thread.   • A simple variable matches a single segment, and a value that contains an encoded / (%2F) is rejected, so that it cannot smuggle path segments such as ..%2F..%2Fetc into the value. A value that may contain / needs a reserved variable, such as {+title}, and clients must send the / encoded, as %2F.

  • A literal / in a variable value is never routed to the method, whatever the operator or the pattern of the variable: the MCP SDK answers with a resource not found error. A regular expression such as {path:.*} does not help, since an encoded / is still rejected in it.

  • A simple variable does not match a literal +, ;, &, !, ( or ), and such a request is answered with an invalid params error. Clients must percent-encode these characters, for example + as %2B.

  • The query is ignored when binding path variables. For book://book/{title}, a request for book://book/a?edition=first binds a. Clients send %3F to include a ? in the value itself.

  • A malformed escape, such as %zz, escaped bytes that are not valid UTF-8, such as %FF, and a value that contains an unpaired surrogate, which a JSON string can carry, are answered with an invalid params error.

Rejecting an encoded / does not make a value safe to use as a path. Decoded values may still be .., contain \ (%5C), control characters such as %00 and a CR LF line break (%0D%0A), which can forge lines in a log, and Unicode look-alikes of /, such as %E2%88%95 (∕), and the values of reserved variables may also contain /. Validate every value before you use it, for example to resolve a file or to build a query.
Several URIs bind the same value: book://book/secret, book://book/%73ecret and book://book/secret?x all bind secret for the template book://book/{title}. Authorize, rate limit and cache on the bound value, never on the URI of the request.

On McpAsyncServer and McpStatelessAsyncServer, addTool, removeTool and the other methods return a Mono that does nothing until it is subscribed to. Subscribe to it, or return it from a reactive method (return server.addTool(spec);), or the primitive is neither added nor removed.

Over STDIO, when micronaut.mcp.server.tools.list-changed (or the prompts or resources equivalent) is true, the server notifies the client that the list changed. Otherwise, clients are not told that the list changed: they see a change only if they call tools/list (or prompts/list, resources/list) again, which many clients do only when they reconnect or start a new session. The HTTP transport cannot send notifications outside the response to a request, so it never advertises list changes or resource subscriptions, whatever the configuration, and its clients are never told. If clients must see changes right away, use the STDIO transport with list-changed set to true.

Adding a primitive with an existing name or URI replaces the current registration. You can also replace or remove primitives declared with annotations, so use trusted names and URIs for these operations.

When multiple callers can register a tool under the same name, serialize their addTool calls. The SDK removes the old tool and adds its replacement in separate steps. Overlapping calls can leave duplicate entries in tools/list. On a reactive server, wait for each registration’s Mono to complete before starting the next registration for that name.

A primitive added at runtime is an MCP Java SDK specification, so its handler receives the SDK request as is. The features of the annotated primitives, such as argument binding, validation, the MCP Request Context and exception mapping, do not apply to it. Only the tool’s inputSchema constrains its arguments, so validate them in the handler or with a strict inputSchema, and keep sensitive details out of exception messages: the client receives the message of an exception the handler throws.

Use either the synchronous or the asynchronous client of a connection, not both. Each client opens its own session over its own transport, which for STDIO would start a second server process, so creating the second client of a connection fails. McpClientTools uses the synchronous client.

A configured client starts its initialization handshake when Micronaut creates the bean. On a blocking thread, creation waits for the handshake. On an event loop, initialization continues in the background and client operations await readiness. If the handshake fails, Micronaut closes the client and its transport and removes the failed singleton. Inject a qualified BeanProvider to resolve a fresh client on a later attempt. When the application stops, the clients are closed gracefully, waiting up to 10 seconds for their transport to close.

The name of a connection declared in configuration is normalized to kebab case: micronaut.mcp.client.http.internalAdmin declares the connection internal-admin, which is also the key of its client. The embeddedServer connection keeps its name.

Each connection needs a name that is unique across micronaut.mcp.client.http and micronaut.mcp.client.stdio. The application fails to start when two connections have the same name, when an HTTP connection has no url, or when a STDIO connection has no command.

Using the tools

For each connection there is a dev.langchain4j.mcp.client.McpClient bean, qualified by the name of the connection, which is also the key of the client (client.key()).

A dev.langchain4j.mcp.McpToolProvider bean provides the tools of every connection to LangChain4j AI services. A McpToolProvider bean qualified by the name of a connection provides only the tools of that connection. The primary provider also includes tools from application-defined McpClient beans. If your application supplies an McpTransport bean, Micronaut creates its DefaultMcpClient.Builder and McpClient beans with the same qualifier.

LangChain4j rejects two tools with the same name, and the primary McpToolProvider gives the tools of every connection under their own names. When two servers have a tool with the same name, every call that uses the primary provider fails, and a server can cause it at any time by renaming or adding a tool. Unless you trust every server, prefix the tools with the name of their connection with an McpToolNameMapper, as shown below, or use the provider of each connection.
The primary McpToolProvider gives the model the tools, and the tool descriptions, of every connection at once. A server you do not fully trust can use its descriptions to steer the model into calling the tools of another connection. Give an AI service the McpToolProvider qualified by the name of the connection it needs, or restrict the tools with an McpToolFilter, rather than the primary provider.

Customizing the tools

Declare one bean of each of these types to customize the tools of all the tool providers. Use the key of the client, the normalized name of its connection, to treat connections differently. Prefer a filter that lists the connections it allows to one that lists those it rejects, so that a name that does not match hides tools rather than exposes them:

  • io.micronaut.mcp.client.langchain4j.McpToolFilter selects the tools that the tool providers provide.

  • io.micronaut.mcp.client.langchain4j.McpToolNameMapper names them.

For example, the following beans prefix every tool with the name of its connection, so that the tools of different servers cannot clash, and only provide the tools of the connections they list, which leaves out, for example, the embeddedServer connection of an application that is itself an MCP server:

@Factory
class McpToolsFactory {

    @Singleton
    McpToolNameMapper prefixWithConnection() {
        return (client, tool) -> client.key() + "__" + tool.name();
    }

    @Singleton
    McpToolFilter onlyListedConnections() {
        return (client, tool) -> Set.of("weather", "files").contains(client.key());
    }
}

Every dev.langchain4j.mcp.client.McpClientListener bean, and a dev.langchain4j.mcp.client.logging.McpLogMessageHandler bean, are registered with every client.

To customize client creation further, define a BeanCreatedEventListener for DefaultMcpClient.Builder, StreamableHttpMcpTransport.Builder or StdioMcpTransport.Builder. A BeanCreatedEventListener for McpToolProvider.Builder customizes the tool providers, both the provider of every connection and the provider of each connection.

Unreachable servers

A client is created when it is first used, which initializes the connection to its server, and starts the process of a STDIO server. The McpToolProvider beans skip the servers that cannot be reached, so an unreachable server does not prevent the application from starting. Creating a client that failed is attempted again the next time the tools are provided. A warning names the connection when its client cannot be created, and an information message when it is created again; the failures in between are logged at debug level.

Only one attempt to create the client of a connection runs at a time. The requests made while it runs do not wait for it: they get no tools from that server. The request that makes an attempt waits up to twice the initialization-timeout of the connection, as the client tries two versions of the protocol, once for each connection whose server cannot be reached, so set a short initialization-timeout for servers that may be unavailable. Each attempt to create the client of a STDIO connection starts a new server process.

By default, each client checks its server periodically with a thread of its own, see auto-health-check.

Health

With Micronaut Management, the mcp health indicator pings every server concurrently, and reports each connection whose server cannot be reached, or whose client cannot be created, as down. The servers that do not answer within endpoints.health.mcp.timeout (default 10s) are reported down. Disable the indicator with endpoints.health.mcp.enabled=false.

The first health check creates the clients that are not created yet, so it starts the processes of the STDIO servers, for example an npx download. While a request is creating the client of a connection, the health check reports that connection down without waiting.

Health checks are not authenticated by default, so anyone who can reach the health endpoint can make the indicator attempt to create the clients that failed, which starts the process of a STDIO server again. Require authentication with endpoints.health.sensitive=true, or serve the management endpoints on a separate port with endpoints.all.port, when the health endpoint is reachable from untrusted networks.
When any server cannot be reached, the mcp indicator is down, so the /health and /health/readiness endpoints answer 503 Service Unavailable; /health/liveness is not affected. A readiness probe on these endpoints takes the application out of service when a server that it can do without is down. The indicator also pings the embeddedServer connection of an application that is itself an MCP server, without credentials, so it is down when that endpoint requires authentication. In these cases, disable the indicator.

Migrating from 2.1

The micronaut.mcp.client.transport property is deprecated and no longer selects the transport: the transport of a connection is set by where it is declared, and connections of both transports can be used together. Its only remaining effect is described below. In particular, micronaut.mcp.client.transport: STDIO no longer removes the embeddedServer connection of an application that is itself an HTTP MCP server, so the tool providers provide the application’s own tools; leave them out with an McpToolFilter, as shown above.

The langchain4j.mcp.client.transport.stdio.commands property is deprecated: as in 2.1, it declares a STDIO connection named stdio only when micronaut.mcp.client.transport is STDIO, and it is ignored otherwise. Declare the connection under micronaut.mcp.client.stdio instead, and note that the property there is command, not commands:

# Before
micronaut.mcp.client.transport: STDIO
langchain4j.mcp.client.transport.stdio.commands: [npx, -y, "@modelcontextprotocol/server-filesystem@<version>", /tmp]

# After
micronaut.mcp.client.stdio.stdio.command: [npx, -y, "@modelcontextprotocol/server-filesystem@<version>", /tmp]

The application logs a warning when it uses either deprecated property. See also the breaking changes.

To compute headers for each request otherwise, for example to send an OAuth access token that is refreshed, declare a bean of type io.micronaut.mcp.conf.client.McpClientHeadersProvider. Both apply to the LangChain4j and the Java SDK clients, and are evaluated on the thread that calls the client: call it from the thread handling the request for the Authorization header to be propagated. The asynchronous Java SDK client evaluates them in the context its subscriber propagates, such as the request a reactive controller is handling.

A headers provider is asked for every connection, unless it overrides supports(McpClientHttpConfiguration): check the connection, so that a token meant for one MCP server is not sent to the others.

Provider headers override static headers even when the names use different capitalization. Connections that propagate authorization or use a headers provider fetch tool, resource, and prompt catalogs on each lookup so the server can select the entries visible to the current caller.

The MCP authorization specification forbids passing through a token whose audience is not the MCP server: a server that follows it rejects the token, and one that skips the audience check becomes a confused deputy. Only propagate the Authorization header to MCP servers that accept the tokens issued for the application, for example servers of the same organization behind the same authorization server. Otherwise exchange the user’s token for one whose audience is the MCP server, for example with OAuth 2.0 Token Exchange, in a custom McpClientHeadersProvider.
The client of a connection, and so its MCP session, is shared by every user of the application: the session is created for the first user, and the propagated Authorization header applies to each request, not to the session. An MCP server that binds its sessions to the user that initialized them, as the specification recommends, rejects or mixes up the calls of other users. Connections that propagate authorization need a server without user-bound sessions, or a connection for each user.

Initialization, pings, reconnections, and replies to server requests can all run outside a user request. If the MCP server requires authentication for those operations, configure a headers provider that can supply application credentials when the current request is absent, for example a client credentials token.

Micronaut HTTP Client

By default the clients send their requests with the JDK HTTP client. Set http-client to MICRONAUT on an HTTP connection to use the Micronaut HTTP client instead, with the micronaut-http-client dependency: the client filters of the application apply, and service-id names the micronaut.http.services entry that configures the client, for example its SSL, proxy or timeouts. The service ID selects filters such as @ClientFilter(serviceId = "weather") even when the service entry omits url. In that case, the connection URL supplies the host. With either HTTP client, a URL without a path uses / for LangChain4j and /mcp for the MCP Java SDK. Without service-id, the default client configuration applies, with the request-timeout of the connection, or its timeout, as the read timeout.

This applies to the LangChain4j and the Java SDK clients. Responses streamed as server-sent events are read as they arrive. A message of the server larger than max-message-size (default 16MB), counted in bytes, fails the request. When the server closes the stream of a response before it sends the response, the client resumes it from its last event, after the retry delay the server sets. The Java SDK client listens to the stream of the messages the server sends on its own, such as the notifications that its tools changed, reconnecting when it ends; as the LangChain4j HTTP transport, the LangChain4j client does not.

The request-timeout or timeout of a connection becomes the read-timeout of its client, and redirects are not followed, since MCP does not use them and following one could send the token of a user to another server. With service-id the micronaut.http.services entry configures the client instead: set its read-timeout and follow-redirects: false there. The read-idle-timeout of the client (default 5m) still applies: it closes the stream of a server that stays quiet that long, and the Java SDK client then reconnects.

The client filters of the application apply to the requests sent to MCP servers, including third-party ones. Restrict the filters that add credentials, for example with @ClientFilter(serviceId = …​) or path patterns, so that they do not reach MCP servers they are not meant for.
The responses are read on the event loop of the Micronaut HTTP client, which by default is shared with the HTTP server. Never call a blocking client API, such as the LangChain4j client or the Java SDK McpSyncClient, on an event loop: it would wait for a response that the blocked event loop cannot read. Call them from a thread that may block, for example with @ExecuteOn(TaskExecutors.BLOCKING), or use the asynchronous Java SDK client. The messages are parsed, and the handlers called, on the blocking executor.

Testing an MCP server

If you are building an MCP Server, you can test it by injecting a bean of type dev.langchain4j.mcp.client.McpClient in your tests. The MCP Client pointing to your MCP Server has a name qualifier with value embeddedServer.
