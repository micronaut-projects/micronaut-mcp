3 Breaking Changes

This section documents breaking changes between Micronaut MCP versions.

2.2.0

  • With the HTTP transport, the requests and notifications handed to the SDK carry their parameters as parsed JSON: McpSchema.JSONRPCRequest.params() and McpSchema.JSONRPCNotification.params() are now an io.micronaut.json.tree.JsonNode (an object or an array) instead of a Map. They are still a Map (or a List) when the application replaces the McpJsonMapper bean, even with a mapper that delegates to the Micronaut one. The SDK handlers convert the parameters with the McpJsonMapper, so this only affects code that replaces or decorates the McpStatelessServerHandler bean and reads params() directly. Such code can convert the parameters with the McpJsonMapper bean, which accepts both forms: mcpJsonMapper.convertValue(request.params(), new TypeRef<Map<String, Object>>() { }).

  • With the HTTP transport, a message that is not a valid JSON-RPC 2.0 request or notification gets HTTP 400 with the JSON-RPC error -32600 (Invalid Request), a null id and a message that names the problem. Before, such a message either got HTTP 500 or reached the SDK. This includes a jsonrpc member that is missing or other than "2.0", a method that is missing or not a string, an id that is null, a boolean, a fractional number or larger than a 64-bit integer, params that are neither an object nor an array, and a batch (an array of messages).

  • With the HTTP transport, an exception other than an McpError that the SDK throws outside your tools, prompts, resources and completions, for example while it converts the request parameters, is logged at ERROR and answered with the JSON-RPC error -32603 and the message Internal error, without the message of the exception. An exception other than an McpError thrown by your prompts, resources and completions is also answered with -32603 and the message Internal error, and logged at WARN with its stack trace, unless an McpErrorExceptionMapper maps it: map the exceptions whose message the client may see. Tools report their failures as tool execution errors instead, see below. A notification whose handling fails is answered with the HTTP status of the error and no body, because a JSON-RPC error response needs an id.

  • A @ToolArg parameter is always a named property of the input schema of a tool, even when its type has a @JsonSchema. Only a parameter without @ToolArg can provide the schema of the whole input.

  • The $id of generated JSON schemas, which clients see in tools/list, defaults to classpath:META-INF/schemas/<name> with Micronaut JSON Schema 2.3.2 and later, instead of http://localhost:8080/schemas/<name>;. Set the micronaut.jsonschema.baseUri annotation processor option to choose another base.

  • A tool method that throws an unmapped exception now returns a result with isError set to true and a generic message identifying the tool. Argument binding and bean validation failures return isError with a message describing the invalid input. With the HTTP transport the response status is 200 instead of 400 or 500. In particular, a bean validation failure of a tool argument is no longer the error -32602. Existing McpErrorExceptionMapper beans still produce JSON-RPC errors for the exceptions they map. To answer with a JSON-RPC error, throw an io.modelcontextprotocol.spec.McpError, or map an exception that Micronaut MCP does not map itself with an McpErrorExceptionMapper. Clients that detect a failed call by the error member of the JSON-RPC response must also check isError in its result. Likewise, access logs, firewall rules and alerts that count 4xx responses no longer see tool arguments that fail validation, which are logged at DEBUG level. See Tool Errors.

  • A tool failure that no McpErrorExceptionMapper maps is logged by the io.micronaut.mcp.server.registry.ToolRegistry logger at WARN level. The registry renders the exception and its stack trace on one log line. A tool that fails often for expected reasons, such as an unknown identifier, should return a CallToolResult whose isError is true instead of throwing, which is not logged. See Tool Errors.

  • The message of a structured content or tool input that does not match its JSON schema lists the schema errors, separated by semicolons, after the prefix the SDK adds, for example Tool (moon-phase-at-date) input validation failed: /date: does not match the date pattern must be a valid RFC 3339 full-date. It no longer contains Validation failed: structuredContent does not match tool outputSchema nor the ValidationMessageAdapter representation of the errors.

  • Every @ResourceTemplate declaration must now specify uriTemplate. Update any declarations that omit it before recompiling.

  • The values of resource template variables are now percent-decoded before they are bound. This is URI decoding: a + is no longer turned into a space, as URLDecoder.decode did. Remove any decoding of the values from your methods, or they are decoded twice: %2525 is bound as %25, which a second decoding turns into %. Values that used to arrive escaped can now contain control characters, such as a CR LF line break from %0D%0A, so methods that log or concatenate them must sanitize them. Malformed escapes, invalid UTF-8, and an encoded / (%2F) in a simple variable such as {path} yield an invalid params error. The same error applies when the SDK routes a URI to a template whose path it fails to match. To accept an encoded /, declare a reserved variable such as {+path}. See Resource Template Variable Decoding.

  • The HTTP endpoint now validates the Origin and MCP-Protocol-Version request headers, as the MCP specification requires. A browser-based client whose origin is neither a loopback origin nor listed in micronaut.mcp.server.transport-security.allowed-origins now gets 403 Forbidden; add its origin to the list (and enable CORS for it). A request with an MCP-Protocol-Version header naming a version the server does not support (it supports 2025-03-26, 2025-06-18 and 2025-11-25) now gets 400 Bad Request. See Transport Security.

4.3.1 Transport

The protocol currently defines two standard transport mechanisms for client-server communication: stdio (communication over standard in and standard out) and Streamable HTTP

For stdio transport, define the property micronaut.mcp.server.transport as STDIO.

For HTTP transport, define the property micronaut.mcp.server.transport as HTTP.

Server to Client communication via an SSE stream is not yet supported. The server responses are currently only of Content-Type: application/json.

4.4 STDIO Transport

If you use Standard Input/Output (stdio) protocol, your server MUST NOT write anything to its stdout.

Disable the Micronaut banner and configure Logback not to log to stdout.

For example, you can configure Logback to log to a file or to stderr (see <target>System.err</target> in the configuration file below):

<configuration>
    <appender name="STDERR" class="ch.qos.logback.core.ConsoleAppender">
        <target>System.err</target>
        <encoder>
            <pattern>%d{HH:mm:ss.SSS} [%thread] %-5level %logger{36} - %msg%n</pattern>
        </encoder>
    </appender>

    <root level="INFO">
        <appender-ref ref="STDERR" />
    </root>
</configuration>

4.6 MCP Transport Context

Micronaut MCP ships MicronautMcpTransportContext, an extension to io.modelcontextprotocol.common.McpTransportContext, which allows you to access concepts such as the authenticated user, locale, host, etc.

With the HTTP transport, the context reads its values from the HTTP request the first time they are asked for, and it keeps the request reachable for as long as the context is reachable. Do not keep the context after the request is handled, for example in a cache or a background task: copy the values you need instead.

The host comes from the request headers (Forwarded, X-Forwarded-Host and Host by default), which the client can set. Do not use it for security decisions, such as building callback URLs or choosing a tenant, unless the host resolution is configured for your proxy, for example with micronaut.server.host-resolution.allowed-hosts.

4.7 Security

Protect the HTTP endpoint of an MCP server against DNS rebinding attacks, and require clients to authenticate.

4.7.1 Transport Security

The HTTP endpoint validates two request headers, as the Streamable HTTP transport requires:

  • Origin, to prevent DNS rebinding attacks. A request whose Origin is not allowed is answered with 403 Forbidden. Requests without an Origin are allowed: browsers always send one, and other clients do not need one. Loopback origins (localhost, 127.0.0.1 and [::1], with http or https and any port) are allowed by default, so that local tools such as the MCP Inspector can connect. Other loopback forms, such as 127.0.0.2 or [::ffff:127.0.0.1], and other schemes, such as the capacitor://localhost of web view shells, are rejected unless listed. Allow the origins of browser-based clients with allowed-origins, or for any origin. Each entry is an origin, scheme://host[:port], without a path, as browsers send it; the default port of http and https can be left out. An entry that is not an origin, such as app.example.com, https://app.example.com/ui, https://app.example.com// or one with a port outside 1 to 65535, could never match, so it fails the startup. Wildcard subdomains, such as https://.example.com, are not supported. Clients that send Origin: null, such as file:// pages and sandboxed iframes, are rejected; only * allows them.

  • MCP-Protocol-Version. A request with a version the server does not support is answered with 400 Bad Request.

A request with more than one Origin header is answered with 403 Forbidden, and one with more than one MCP-Protocol-Version header with 400 Bad Request, so that a second value cannot pass for the one that is checked. The checks apply to every request routed to the MCP endpoint, whatever the shape of micronaut.mcp.server.endpoint and the context path; a request with a method the endpoint does not serve is answered with 405 Method Not Allowed.

The headers are checked by a filter on the MCP endpoint, before the request body is read. It runs after the CORS filter, so that a browser can read the rejection, and before authentication, so that a request from a foreign origin is answered with 403 rather than 401. Turn on DEBUG logging for io.micronaut.mcp.server.stateless to see why a request was rejected.

Validation is enabled by default, as the specification requires servers to validate the Origin header. It can be disabled with enabled: false (only the value false disables it), for example when a gateway in front of the server validates the Origin. Disabling it turns off both checks, including the MCP-Protocol-Version check, which gateways usually do not perform. The transport security properties are read at startup: changing them, for example through a refresh of the configuration, takes effect after a restart.

micronaut.mcp.server.transport-security.allowed-origins[0]=https://app.example.com

To allow only known local tools, set allow-loopback-origins to false and list them with their ports in allowed-origins, for example http://localhost:6274. Do the same on a server reachable from other hosts.

A browser-based client on another origin also needs CORS to be enabled for that origin. Its MCP requests are POST requests with a JSON body, and usually an Authorization and an MCP-Protocol-Version header, so the browser first sends a preflight OPTIONS request, which the Micronaut CORS configuration must allow, including those headers. The allowed origins of the MCP endpoint do not configure CORS, and CORS does not configure them: an origin allowed by CORS but not listed in allowed-origins gets 403 Forbidden. The specification requires the server to accept only tokens issued for it, so that a token issued for another service cannot be used against the MCP server. Set the audience to the canonical URL of your MCP endpoint. Validate the issuer too, so that a token of another issuer that shares the provider’s keys, such as another tenant, is rejected, and the not-before time.

Micronaut Security accepts a token without an expiration (exp). If your provider can issue such tokens, register a GenericJwtClaimsValidator bean whose validate method returns claims.contains(Claims.EXPIRATION_TIME), so that a leaked token cannot be used forever.

Serve the endpoint over HTTPS only, with micronaut.server.ssl or behind a proxy that terminates TLS, as the bearer tokens are sent with every request.

The WWW-Authenticate challenge and the resource of the protected resource metadata are built from the host the request names, in its Host or forwarded headers. List the hosts of the server in micronaut.server.host-resolution.allowed-hosts, regular expressions matched against scheme://host[:port], so that a forged host, for example in a cached response, cannot send clients to another authorization server. A request whose host matches none of them is resolved to http://localhost, so clients would look for the metadata on their own machine. With the allowed hosts set, the resource is the canonical URL of the endpoint, the audience above.

If you change micronaut.mcp.server.endpoint, update the intercept-url-map pattern and the JWT audience to match the new path. Publish a single canonical endpoint URL without a trailing slash. Micronaut’s router accepts a trailing-slash alias, but the stock challenge uses the request path and the metadata may omit the slash from its resource. Clients following RFC 9728 reject that mismatch. If you expose the alias, configure your proxy or an application request filter to return a 308 Permanent Redirect to the canonical path before authentication. A 308 preserves the POST method and body.

If you set micronaut.server.context-path, the stock metadata controller is mounted under that context path. The public metadata URL in the challenge still starts at the origin root, so configure your proxy to forward it to the controller.   • A class or Java record which will be serialized to JSON. If the return type is annotated with @JsonSchema and it is defined as the tool output it will be used as structured content.

Any of these can also be produced asynchronously, by returning a single value reactive type such as Mono<T>, a Publisher<T> that emits at most one value, or a CompletionStage<T>. Other reactive types, such as RxJava’s Single, are converted with the conversion service. The value it produces is used as if the method had returned it, and the result is chosen from that value rather than from the declared return type. A @JsonSchema type produced this way is still used as the structured output; producing no value is then a tool error.

A method returning a type that may emit several values, such as Flux<T>, fails the startup, unless it is annotated with @SingleResult. A Publisher<T> that emits more than one value fails the call.

The single-value rules also apply to methods annotated with @Prompt, @Resource, @ResourceTemplate, @PromptCompletion and @ResourceCompletion.

A @PromptCompletion or @ResourceCompletion method can also return a Flux<String> of suggestions. The response contains up to 100 suggestions in emission order. If the publisher emits a 101st suggestion, the server cancels the subscription, sets hasMore to true, and omits the unknown total.

How the methods are invoked depends on micronaut.mcp.server.reactive:

  • When it is false (the default), the HTTP endpoint handles requests on the blocking executor, which uses virtual threads where they are available. Methods run on that thread, can block, and see the current request through ServerRequestContext. The server waits for asynchronous return values. A method annotated with @ExecuteOn runs on the named executor, for example to limit how many calls run concurrently, and the request thread waits for the result. If you configure a fixed-size HTTP blocking executor, use a separate executor for asynchronous work that a request waits for, or enable the reactive server.

  • When it is true, methods run on the thread that received the request, which must not block. Annotate a method with @ExecuteOn to run it on another executor, for example @ExecuteOn(TaskExecutors.BLOCKING).

See Tool Errors for how a tool reports a failure.

  • For an expected failure, return a CallToolResult with isError set to true and a message that helps the caller correct the request. For example, temperature lists the supported cities. Returning an error result does not generate a server log entry.

  • If a tool throws an unmapped exception, the client receives a tool execution error with a generic message, such as Tool forecast failed. Clients decide what to show the model. The MCP specification recommends that clients forward tool execution errors and allows them to forward protocol errors too. Use client-safe text in explicit results and in the message and data of a protocol error.

Arguments that cannot be bound or fail bean validation produce tool execution errors with the validation message, for example date: must be a date in the past or in the present. The registry logs these errors at DEBUG.

An application io.micronaut.mcp.server.exceptions.McpErrorExceptionMapper can turn an exception into a protocol error. A mapper that matches every RuntimeException also matches an McpError thrown by a tool and can replace its code and message. The built-in argument mappers send their messages as tool execution errors. They match by exception type, including when a tool body throws an exception such as a SerdeException while reading an upstream response. The registry unwraps exceptions from reactive types and CompletionStage before choosing a mapper. The same rules apply to synchronous and reactive servers. Prompts, resources and completions report failures as protocol errors.

With a reactive server, a tool without @ExecuteOn can fail on the event loop. A synchronous appender writes the log on that thread. An asynchronous appender such as Logback’s AsyncAppender can offload that work. The registry renders unexpected tool exceptions, including their causes and suppressed exceptions, on one log line.

  • A simple variable matches a single segment, and a value that contains an encoded / (%2F) is rejected, so that it cannot smuggle path segments such as ..%2F..%2Fetc into the value. A value that may contain / needs a reserved variable, such as {+title}, and clients must send the / encoded, as %2F.

  • A literal / in a variable value is never routed to the method, whatever the operator or the pattern of the variable: the MCP SDK answers with a resource not found error. A regular expression such as {path:.*} does not help, since an encoded / is still rejected in it.

  • A simple variable does not match a literal +, ;, &, !, ( or ), and such a request is answered with an invalid params error. Clients must percent-encode these characters, for example + as %2B.

  • The query is ignored when binding path variables. For book://book/{title}, a request for book://book/a?edition=first binds a. Clients send %3F to include a ? in the value itself.

  • A malformed escape, such as %zz, escaped bytes that are not valid UTF-8, such as %FF, and a value that contains an unpaired surrogate, which a JSON string can carry, are answered with an invalid params error.

Rejecting an encoded / does not make a value safe to use as a path. Decoded values may still be .., contain \ (%5C), control characters such as %00 and a CR LF line break (%0D%0A), which can forge lines in a log, and Unicode look-alikes of /, such as %E2%88%95 (∕), and the values of reserved variables may also contain /. Validate every value before you use it, for example to resolve a file or to build a query.
Several URIs bind the same value: book://book/secret, book://book/%73ecret and book://book/secret?x all bind secret for the template book://book/{title}. Authorize, rate limit and cache on the bound value, never on the URI of the request.

Every @Icon requires a src that is an HTTPS URL or a data:image/…​ URI (an HTTP URL is accepted, for example for local development) without a user name or password, and its theme, when set, must be light or dark in lowercase. An image data URI needs an image media type and a non-empty payload separated by a comma. An invalid icon causes startup to fail.

Icons are repeated in every list response that includes their primitive. When many primitives share an icon, prefer an HTTPS URL over a data: URI to keep the responses small. Clients should treat icons, SVG ones in particular, as untrusted content.

A @Meta key must be non-empty and follow the MCP key format. For example, com.example/display-name has the prefix com.example/ and the name display-name. MCP reserves prefixes whose second label is modelcontextprotocol or mcp, such as io.modelcontextprotocol/.

Repeating the same key and value on a method produces one metadata entry. A malformed key or conflicting values for the same key cause startup to fail.

The values of @Meta are always strings. For numbers, booleans or objects, define the primitive with a factory instead (see Tools with a Factory, Prompts with a Factory and Resources with a Factory) and set its _meta there.
