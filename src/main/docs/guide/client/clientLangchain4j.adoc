To use an https://docs.langchain4j.dev/tutorials/mcp#mcp-client[MCP Client powered by LangChain4j], use the following dependency:

dependency:micronaut-mcp-client-langchain4j[groupId=io.micronaut.mcp]

=== Connections

Declare a named connection for each MCP server, over Streamable HTTP or STDIO. Connections of both transports can be used together:

[configuration]
----
micronaut:
  mcp:
    client:
      http:
        weather:
          url: https://weather.example.com/mcp
          headers:
            Authorization: Bearer ${WEATHER_TOKEN}
          request-timeout: 30s
      stdio:
        files:
          command:
            - npx
            - -y
            - "@modelcontextprotocol/server-filesystem@<version>"
            - /tmp
          environment:
            DEBUG: "false"
          initialization-timeout: 2m
          auto-health-check: false
----

The name of a connection declared in configuration is normalized to kebab case: `micronaut.mcp.client.http.internalAdmin` declares the connection `internal-admin`, which is also the key of its client. The `embeddedServer` connection keeps its name.

Each connection needs a name that is unique across `micronaut.mcp.client.http` and `micronaut.mcp.client.stdio`. The application fails to start when two connections have the same name, when an HTTP connection has no `url`, or when a STDIO connection has no `command`.

.Settings of a connection
|===
|Setting |Transport |Description |Default

|`url` |HTTP |The URL of the MCP endpoint of the server. Required. |
|`headers` |HTTP |The headers sent with every request, such as `Authorization`. |
|`timeout` |HTTP |The timeout of the HTTP calls of the transport. |
|`log-requests`, `log-responses` |HTTP |Whether to log the HTTP requests and responses. |`false`
|`command` |STDIO |The command that starts the server, and its arguments. Required. |
|`environment` |STDIO |The environment variables of the server process, in addition to those of the application. |
|`log-events` |STDIO |Whether to log the messages exchanged with the server. |`false`
|`initialization-timeout` |Both |How long to wait for the server to answer the initialization. |`30s`
|`request-timeout` |Both |How long to wait for the server to answer an MCP request, such as a tool call or a ping. |`60s`, and `10s` for pings
|`auto-health-check` |Both |Whether the client checks periodically that its server is reachable, and reconnects when it is not. |`true`
|===

NOTE: Keys of `headers` and `environment` keep their case when set in a configuration file. When they are set with environment variables, such as `MICRONAUT_MCP_CLIENT_STDIO_FILES_ENVIRONMENT_DEBUG`, they are lower-cased, so the server process receives `debug` rather than `DEBUG`. Set keys whose case matters in a configuration file.

NOTE: The process of a STDIO connection inherits the environment of the application, in addition to its `environment`. Applications that keep secrets in their environment make them available to that process, so only start servers you trust, pin their version, for example `@modelcontextprotocol/server-filesystem@<version>` rather than the latest release that `npx` would download, and consider starting them with a cleared environment, for example `command: [env, -i, "PATH=/usr/bin:/bin", npx, ...]`. Pass secrets to a server in its `environment` rather than in its `command`, as the command is logged at debug level.

For STDIO connections, a reconnection by `auto-health-check` starts a new server process, so consider disabling it for servers that are slow to start, such as those started with `npx`, or that cannot run twice.

=== Using the tools

For each connection there is a `dev.langchain4j.mcp.client.McpClient` bean, qualified by the name of the connection, which is also the key of the client (`client.key()`).

A `dev.langchain4j.mcp.McpToolProvider` bean provides the tools of every connection to LangChain4j AI services. A `McpToolProvider` bean qualified by the name of a connection provides only the tools of that connection. The primary provider also includes tools from application-defined `McpClient` beans. If your application supplies an `McpTransport` bean, Micronaut creates its `DefaultMcpClient.Builder` and `McpClient` beans with the same qualifier.

WARNING: LangChain4j rejects two tools with the same name, and the primary `McpToolProvider` gives the tools of every connection under their own names. When two servers have a tool with the same name, every call that uses the primary provider fails, and a server can cause it at any time by renaming or adding a tool. Unless you trust every server, prefix the tools with the name of their connection with an `McpToolNameMapper`, as shown below, or use the provider of each connection.

WARNING: The primary `McpToolProvider` gives the model the tools, and the tool descriptions, of every connection at once. A server you do not fully trust can use its descriptions to steer the model into calling the tools of another connection. Give an AI service the `McpToolProvider` qualified by the name of the connection it needs, or restrict the tools with an `McpToolFilter`, rather than the primary provider.

=== Customizing the tools

Declare one bean of each of these types to customize the tools of all the tool providers. Use the key of the client, the normalized name of its connection, to treat connections differently. Prefer a filter that lists the connections it allows to one that lists those it rejects, so that a name that does not match hides tools rather than exposes them:

- `io.micronaut.mcp.client.langchain4j.McpToolFilter` selects the tools that the tool providers provide.
- `io.micronaut.mcp.client.langchain4j.McpToolNameMapper` names them.

For example, the following beans prefix every tool with the name of its connection, so that the tools of different servers cannot clash, and only provide the tools of the connections they list, which leaves out, for example, the `embeddedServer` connection of an application that is itself an MCP server:

[source,java]
----
@Factory
class McpToolsFactory {

    @Singleton
    McpToolNameMapper prefixWithConnection() {
        return (client, tool) -> client.key() + "__" + tool.name();
    }

    @Singleton
    McpToolFilter onlyListedConnections() {
        return (client, tool) -> Set.of("weather", "files").contains(client.key());
    }
}
----

Every `dev.langchain4j.mcp.client.McpClientListener` bean, and a `dev.langchain4j.mcp.client.logging.McpLogMessageHandler` bean, are registered with every client.

To customize client creation further, define a
https://docs.micronaut.io/latest/api/io/micronaut/context/event/BeanCreatedEventListener.html[BeanCreatedEventListener]
for `DefaultMcpClient.Builder`, `StreamableHttpMcpTransport.Builder` or `StdioMcpTransport.Builder`. A `BeanCreatedEventListener` for `McpToolProvider.Builder` customizes the tool providers, both the provider of every connection and the provider of each connection.

=== Unreachable servers

A client is created when it is first used, which initializes the connection to its server, and starts the process of a STDIO server. The `McpToolProvider` beans skip the servers that cannot be reached, so an unreachable server does not prevent the application from starting. Creating a client that failed is attempted again the next time the tools are provided. A warning names the connection when its client cannot be created, and an information message when it is created again; the failures in between are logged at debug level.

Only one attempt to create the client of a connection runs at a time. The requests made while it runs do not wait for it: they get no tools from that server. The request that makes an attempt waits up to twice the `initialization-timeout` of the connection, as the client tries two versions of the protocol, once for each connection whose server cannot be reached, so set a short `initialization-timeout` for servers that may be unavailable. Each attempt to create the client of a STDIO connection starts a new server process.

By default, each client checks its server periodically with a thread of its own, see `auto-health-check`.

=== Health

With Micronaut Management, the `mcp` health indicator pings every server concurrently, and reports each connection whose server cannot be reached, or whose client cannot be created, as down. The servers that do not answer within `endpoints.health.mcp.timeout` (default `10s`) are reported down. Disable the indicator with `endpoints.health.mcp.enabled=false`.

The first health check creates the clients that are not created yet, so it starts the processes of the STDIO servers, for example an `npx` download. While a request is creating the client of a connection, the health check reports that connection down without waiting.

WARNING: Health checks are not authenticated by default, so anyone who can reach the health endpoint can make the indicator attempt to create the clients that failed, which starts the process of a STDIO server again. Require authentication with `endpoints.health.sensitive=true`, or serve the management endpoints on a separate port with `endpoints.all.port`, when the health endpoint is reachable from untrusted networks.

WARNING: When any server cannot be reached, the `mcp` indicator is down, so the `/health` and `/health/readiness` endpoints answer `503 Service Unavailable`; `/health/liveness` is not affected. A readiness probe on these endpoints takes the application out of service when a server that it can do without is down. The indicator also pings the `embeddedServer` connection of an application that is itself an MCP server, without credentials, so it is down when that endpoint requires authentication. In these cases, disable the indicator.

=== Migrating from 2.1

The `micronaut.mcp.client.transport` property is deprecated and no longer selects the transport: the transport of a connection is set by where it is declared, and connections of both transports can be used together. Its only remaining effect is described below. In particular, `micronaut.mcp.client.transport: STDIO` no longer removes the `embeddedServer` connection of an application that is itself an HTTP MCP server, so the tool providers provide the application's own tools; leave them out with an `McpToolFilter`, as shown above.

The `langchain4j.mcp.client.transport.stdio.commands` property is deprecated: as in 2.1, it declares a STDIO connection named `stdio` only when `micronaut.mcp.client.transport` is `STDIO`, and it is ignored otherwise. Declare the connection under `micronaut.mcp.client.stdio` instead, and note that the property there is `command`, not `commands`:

[source,yaml]
----
# Before
micronaut.mcp.client.transport: STDIO
langchain4j.mcp.client.transport.stdio.commands: [npx, -y, "@modelcontextprotocol/server-filesystem@<version>", /tmp]

# After
micronaut.mcp.client.stdio.stdio.command: [npx, -y, "@modelcontextprotocol/server-filesystem@<version>", /tmp]
----

The application logs a warning when it uses either deprecated property. See also the <<breaks, breaking changes>>.

=== Authorization

To call MCP servers on behalf of the user, set `propagate-authorization` on an HTTP connection: the `Authorization` header of the HTTP request the application is handling, such as the user's bearer token, is sent to the MCP server. Only bearer tokens are propagated; set `propagate-any-authorization-scheme` to also propagate other schemes, such as Basic credentials.

[configuration]
----
micronaut:
  mcp:
    client:
      http:
        weather:
          url: https://weather.example.com/mcp
          propagate-authorization: true
----

To compute headers for each request otherwise, for example to send an OAuth access token that is refreshed, declare a bean of type `io.micronaut.mcp.conf.client.McpClientHeadersProvider`. Both apply to the LangChain4j and the Java SDK clients, and are evaluated on the thread that calls the client: call it from the thread handling the request for the `Authorization` header to be propagated. The asynchronous Java SDK client evaluates them in the context its subscriber propagates, such as the request a reactive controller is handling.

A headers provider is asked for every connection, unless it overrides `supports(McpClientHttpConfiguration)`: check the connection, so that a token meant for one MCP server is not sent to the others.

Provider headers override static headers even when the names use different capitalization. Connections that propagate authorization or use a headers provider fetch tool, resource, and prompt catalogs on each lookup so the server can select the entries visible to the current caller.

WARNING: The https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization[MCP authorization specification] forbids passing through a token whose audience is not the MCP server: a server that follows it rejects the token, and one that skips the audience check becomes a confused deputy. Only propagate the `Authorization` header to MCP servers that accept the tokens issued for the application, for example servers of the same organization behind the same authorization server. Otherwise exchange the user's token for one whose audience is the MCP server, for example with https://datatracker.ietf.org/doc/html/rfc8693[OAuth 2.0 Token Exchange], in a custom `McpClientHeadersProvider`.

IMPORTANT: The client of a connection, and so its MCP session, is shared by every user of the application: the session is created for the first user, and the propagated `Authorization` header applies to each request, not to the session. An MCP server that binds its sessions to the user that initialized them, as the specification recommends, rejects or mixes up the calls of other users. Connections that propagate authorization need a server without user-bound sessions, or a connection for each user.

Initialization, pings, reconnections, and replies to server requests can all run outside a user request. If the MCP server requires authentication for those operations, configure a headers provider that can supply application credentials when the current request is absent, for example a client credentials token.

=== Micronaut HTTP Client

By default the clients send their requests with the JDK HTTP client. Set `http-client` to `MICRONAUT` on an HTTP connection to use the Micronaut HTTP client instead, with the `micronaut-http-client` dependency: the client filters of the application apply, and `service-id` names the `micronaut.http.services` entry that configures the client, for example its SSL, proxy or timeouts. The service ID selects filters such as `@ClientFilter(serviceId = "weather")` even when the service entry omits `url`. In that case, the connection URL supplies the host. A `url` without a path sends the requests to `/mcp`, as with the JDK HTTP client. Without `service-id`, the default client configuration applies, with the `request-timeout` of the connection, or its `timeout`, as the read timeout.

[configuration]
----
micronaut:
  mcp:
    client:
      http:
        weather:
          url: https://weather.example.com/mcp
          http-client: MICRONAUT
          service-id: weather
  http:
    services:
      weather:
        read-timeout: 60s
        follow-redirects: false
----

This applies to the LangChain4j and the Java SDK clients. Responses streamed as server-sent events are read as they arrive. A message of the server larger than `max-message-size` (default `16MB`), counted in bytes, fails the request. When the server closes the stream of a response before it sends the response, the client resumes it from its last event, after the `retry` delay the server sets. The Java SDK client listens to the stream of the messages the server sends on its own, such as the notifications that its tools changed, reconnecting when it ends; as the LangChain4j HTTP transport, the LangChain4j client does not.

The `request-timeout` or `timeout` of a connection becomes the `read-timeout` of its client, and redirects are not followed, since MCP does not use them and following one could send the token of a user to another server. With `service-id` the `micronaut.http.services` entry configures the client instead: set its `read-timeout` and `follow-redirects: false` there. The `read-idle-timeout` of the client (default `5m`) still applies: it closes the stream of a server that stays quiet that long, and the Java SDK client then reconnects.

WARNING: The client filters of the application apply to the requests sent to MCP servers, including third-party ones. Restrict the filters that add credentials, for example with `@ClientFilter(serviceId = ...)` or path patterns, so that they do not reach MCP servers they are not meant for.

WARNING: The responses are read on the event loop of the Micronaut HTTP client, which by default is shared with the HTTP server. Never call a blocking client API, such as the LangChain4j client or the Java SDK `McpSyncClient`, on an event loop: it would wait for a response that the blocked event loop cannot read. Call them from a thread that may block, for example with `@ExecuteOn(TaskExecutors.BLOCKING)`, or use the asynchronous Java SDK client. The messages are parsed, and the handlers called, on the blocking executor.

=== Testing an MCP server

If you are building an MCP Server, you can test it by injecting a bean of type `dev.langchain4j.mcp.client.McpClient` in your tests.
The MCP Client pointing to your MCP Server has a name qualifier with value `embeddedServer`.
