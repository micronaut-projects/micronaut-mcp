This section documents breaking changes between Micronaut MCP versions.

=== 2.2.0

* With the HTTP transport, the requests and notifications handed to the SDK carry their parameters as parsed JSON: `McpSchema.JSONRPCRequest.params()` and `McpSchema.JSONRPCNotification.params()` are now an `io.micronaut.json.tree.JsonNode` (an object or an array) instead of a `Map`. They are still a `Map` (or a `List`) when the application replaces the `McpJsonMapper` bean, even with a mapper that delegates to the Micronaut one. The SDK handlers convert the parameters with the `McpJsonMapper`, so this only affects code that replaces or decorates the `McpStatelessServerHandler` bean and reads `params()` directly. Such code can convert the parameters with the `McpJsonMapper` bean, which accepts both forms: `mcpJsonMapper.convertValue(request.params(), new TypeRef<Map<String, Object>>() { })`.
* With the HTTP transport, a message that is not a valid JSON-RPC 2.0 request or notification gets HTTP 400 with the JSON-RPC error `-32600` (Invalid Request), a `null` id and a message that names the problem. Before, such a message either got HTTP 500 or reached the SDK. This includes a `jsonrpc` member that is missing or other than `"2.0"`, a `method` that is missing or not a string, an `id` that is `null`, a boolean, a fractional number or larger than a 64-bit integer, `params` that are neither an object nor an array, and a batch (an array of messages).
* With the HTTP transport, an exception other than an `McpError` that the SDK throws outside your tools, prompts, resources and completions, for example while it converts the request parameters, is logged at `ERROR` and answered with the JSON-RPC error `-32603` and the message `Internal error`, without the message of the exception. Exceptions thrown by your own primitives are still reported to the client with their message, unless an `McpErrorExceptionMapper` maps them. A notification whose handling fails is answered with the HTTP status of the error and no body, because a JSON-RPC error response needs an id.
* A `@ToolArg` parameter is always a named property of the input schema of a tool, even when its type has a `@JsonSchema`. Only a parameter without `@ToolArg` can provide the schema of the whole input.
* The `$id` of generated JSON schemas, which clients see in `tools/list`, defaults to `classpath:META-INF/schemas/<name>` with Micronaut JSON Schema 2.3.2 and later, instead of `http://localhost:8080/schemas/<name>`. Set the `micronaut.jsonschema.baseUri` annotation processor option to choose another base.
* Tools, prompts and resources declared on singleton beans keep the bean instance they first resolve, so they keep using it after `destroyBean` or `refreshBean`.
