This section documents breaking changes between Micronaut MCP versions.

=== 2.2.0

* With the HTTP transport, the request handed to the SDK carries its parameters as parsed JSON: `McpSchema.JSONRPCRequest.params()` is now an `io.micronaut.json.tree.JsonNode` instead of a `Map`. The SDK handlers convert the parameters with the `McpJsonMapper`, so this only affects code that decorates `McpStatelessServerHandler` and reads `params()` directly.
* The `uriTemplate` member of `@ResourceTemplate` no longer has a default value, so every `@ResourceTemplate` must declare it. A template without one could never match a request.
* The values of resource template variables are now percent-decoded before they are bound. A simple variable whose decoded value contains `/`, and a value with a malformed escape, are answered with an invalid params error.
* The HTTP endpoint now validates the `Origin` and `MCP-Protocol-Version` request headers, as the MCP specification requires. A browser-based client whose origin is neither a loopback origin nor listed in `micronaut.mcp.server.transport-security.allowed-origins` now gets `403 Forbidden`; add its origin to the list (and enable CORS for it). See <<security, Security>>.
* A `@ToolArg` parameter is always a named property of the input schema of a tool, even when its type has a `@JsonSchema`. Only a parameter without `@ToolArg` can provide the schema of the whole input.
* The `$id` of generated JSON schemas, which clients see in `tools/list`, defaults to `classpath:META-INF/schemas/<name>` with Micronaut JSON Schema `2.3.2-SNAPSHOT`, instead of `http://localhost:8080/schemas/<name>`. Set the `micronaut.jsonschema.baseUri` annotation processor option to choose another base.
* Tools, prompts and resources declared on singleton beans keep the bean instance they first resolve, so they keep using it after `destroyBean` or `refreshBean`.
* Stateless servers no longer advertise `listChanged` or `subscribe`, even when `list-changed` or `subscribe` is configured, since they cannot send notifications outside the response to a request.
* The LangChain4j MCP client connects to every connection of `micronaut.mcp.client.http` and `micronaut.mcp.client.stdio` together. `micronaut.mcp.client.transport` is deprecated and no longer selects the transport: with `STDIO`, the HTTP connections, including the `embeddedServer` connection of an application that is itself an HTTP MCP server, are no longer left out, so their tools reach the `McpToolProvider`. Remove the HTTP connections you do not want, and leave out the tools of `embeddedServer` with an `McpToolFilter`. See <<clientLangchain4j, LangChain4j MCP Client>>.
* The `McpToolProvider` of the LangChain4j client skips the servers that cannot be reached instead of failing, and connects to each server when its client is first used rather than when the provider is created. While one request creates the client of a connection, the other requests get no tools from that server instead of waiting.
* With Micronaut Management, the new `mcp` health indicator of the LangChain4j client is down when any server cannot be reached, so `/health` and `/health/readiness` answer `503`. Disable it with `endpoints.health.mcp.enabled=false`.
* The LangChain4j `StdioMcpTransport` and `StreamableHttpMcpTransport` beans are prototypes owned and closed by their client, instead of singletons. Inject the `McpClient` of a connection rather than its transport.
* The application fails to start when two MCP client connections have the same name, when an HTTP connection has no `url`, or when a STDIO connection has no `command`.
