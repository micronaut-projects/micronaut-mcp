The server records metrics for its operations; it does not create tracing spans. HTTP metrics and traces of the MCP endpoint come from Micronaut Micrometer and Micronaut Tracing as usual, but they group every MCP operation under one URI. The timer described here splits them by method and primitive.

To record metrics, add https://micronaut-projects.github.io/micronaut-micrometer/latest/guide/[Micronaut Micrometer] and a meter registry, for example Prometheus:

dependency:micronaut-micrometer-core[groupId=io.micronaut.micrometer]

dependency:micronaut-micrometer-registry-prometheus[groupId=io.micronaut.micrometer]

To expose the metrics at `/prometheus`, as the https://micronaut-projects.github.io/micronaut-micrometer/latest/guide/[Micronaut Micrometer guide] describes, also add Micronaut Management:

dependency:micronaut-management[groupId=io.micronaut]

WARNING: The metrics name every tool, prompt and resource of the server and show how often each is used and fails. The MCP endpoint is reachable by remote clients, and management endpoints share its port by default, so do not make `/prometheus` available without authentication on that port. Either keep the endpoint sensitive and have the scraper authenticate (with Micronaut Security, a sensitive endpoint requires an authenticated request), or serve the management endpoints on a separate port that only the monitoring network can reach:

[source,properties]
----
endpoints.all.port=8081
endpoints.prometheus.sensitive=false
----

The server then times these operations with a timer named `mcp.server.operation.duration`:

* calls of annotated tools (`tools/call`)
* gets of annotated prompts (`prompts/get`)
* reads of annotated resources and resource templates (`resources/read`)
* annotated completions (`completion/complete`)

|===
|Tag |Value

|`mcp.method.name`
|The JSON-RPC method: `tools/call`, `prompts/get`, `resources/read` or `completion/complete`

|`mcp.primitive.name`
|The name of the tool or prompt; the URI of the resource; the URI template, as declared, of the resource template, not the URI that was read; or, for a completion, the name of the prompt or the URI of the resource it completes

|`error.type`
a|* `none` on success.
* `tool_error` when a tool call returns a tool execution error: the tool threw an exception, or the model sent arguments that could not be bound or validated.
* Otherwise, the JSON-RPC error code of the protocol error the operation ended with. An exception thrown by a prompt, resource or completion method is `-32603` (internal error), unless an `McpErrorExceptionMapper` maps it to another code; so is an exception thrown by a tool that such a mapper maps.
* `_OTHER` for a protocol error whose code is outside the range JSON-RPC reserves (-32768 to -32000), which holds every code of JSON-RPC and MCP. Such a code is defined by the application and may come from a remote peer, for example a tool that relays the errors of another MCP server, so it is not reported, to keep the number of timers bounded.
* `cancelled` when the reactive server cancelled the result before it produced a value.
* The fully qualified class name of a JVM `Error` the method threw, for example `java.lang.StackOverflowError`. An `Error` that reaches the server through a returned publisher or future, or that a method declaring `@ExecuteOn` throws on the synchronous server, is handled like an exception.
|===

The Prometheus registry renders the timer with Prometheus names, for example:

[source]
----
mcp_server_operation_duration_seconds_count{error_type="none",mcp_method_name="tools/call",mcp_primitive_name="weather"} 12
----

For example, the rate of failed calls of each tool is:

[source]
----
sum by (mcp_primitive_name) (rate(mcp_server_operation_duration_seconds_count{mcp_method_name="tools/call",error_type!="none"}[5m]))
----

Primitives added at runtime through the MCP Java SDK server (see <<dynamicPrimitives, Adding Primitives at Runtime>>), and requests the SDK rejects before dispatching them, for example a call of an unknown tool, are not timed.

The timer is based on the https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/mcp.md[OpenTelemetry semantic conventions for MCP], which are still in development, with these differences:

* The conventions name the primitive with `gen_ai.tool.name`, `gen_ai.prompt.name` or the opt-in `mcp.resource.uri`, depending on the operation. The timer always uses `mcp.primitive.name`, a tag Micronaut MCP defines, not the conventions, because the Prometheus registry requires every timer of a name to have the same tag keys.
* The conventions leave `error.type` out on success. The timer sets it to `none`, for the same reason.
* The conventions do not count some JSON-RPC error codes as errors, for example `-32602` (invalid params). The timer records every reserved code in `error.type`, so that a dashboard can tell them apart from successes.
* The conventions time a request from when it is received until its response is sent. The timer covers only the method of the primitive: from when the server invokes it, including any wait for the executor of `@ExecuteOn`, until its result is mapped. The JSON-RPC parsing, the input validation of the SDK and the serialization of the response are not included.

With a meter registry that accepts different tag keys for one meter name, a https://docs.micrometer.io/micrometer/reference/concepts/meter-filters.html[Micrometer `MeterFilter`] bean can map `mcp.primitive.name` to the attribute names of the conventions.

The timer publishes no histogram buckets by default, so Prometheus cannot compute percentiles such as the 95th. To publish them, register a `MeterFilter` bean whose `configure` method, for the meter named `mcp.server.operation.duration`, merges service level objectives into the distribution statistics, for example the bucket boundaries the conventions recommend: 0.01, 0.025, 0.05, 0.1, 0.25, 0.5, 1, 2.5, 5, 10, 30, 60, 120 and 300 seconds.

The timer is on by default whenever a `MeterRegistry` bean exists. Disable it with `micronaut.mcp.server.metrics.enabled=false`; your own observers still run. Disabling Micrometer itself with `micronaut.metrics.enabled=false` disables it too.

To observe operations otherwise, register a bean of type api:mcp.server.observability.McpServerObserver[]: it is notified when each operation starts and ends. Each observation is stopped exactly once, including on the reactive server. Observers are called on the thread that runs the operation, which may be an event loop, so they must return quickly and never block. An observer that throws is logged and does not fail the operation. The interface is experimental and may change, for example to give observers the context of the request.
