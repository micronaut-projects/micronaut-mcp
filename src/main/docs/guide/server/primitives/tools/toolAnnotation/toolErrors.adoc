A method annotated with `@Tool` reports a failure in one of three ways, which the following tools show:

snippet::io.micronaut.mcp.docs.tools.errors.WeatherTools[project-base="test-suite-docs", tags="fakepackage,imports,clazz"]

- An expected failure that the model can correct, such as the unknown city of `temperature`: return a `CallToolResult` whose `isError` is `true`, with a message that tells the model what to do. Nothing is logged.
- An unexpected failure, such as the unavailable service of `forecast`: throw an exception. The call returns a result whose `isError` is `true` and whose text is the message of the exception. This is a https://modelcontextprotocol.io/specification/2025-11-25/server/tools#error-handling[tool execution error]: the model sees it and can try again or tell the user. The exception is logged at `WARN` level with its stack trace. When `micronaut.mcp.server.reactive` is `true`, a method without `@ExecuteOn` fails on the thread that received the request, so a synchronous appender writes that log on the event loop; use an asynchronous appender, such as Logback's `AsyncAppender`, if tools fail often. Since any caller can make a tool fail, consider rate limiting the MCP endpoint. Control characters, such as line breaks, are replaced in the logged message, so that a caller cannot forge log lines through it, but the stack trace logged with it still contains the original message: use an encoder that escapes line breaks, such as a JSON encoder, if logs are parsed line by line.
- A failure that the model should not see, such as the disabled alerts of `alerts`: throw an `io.modelcontextprotocol.spec.McpError`. The call is answered with a JSON-RPC protocol error with its code and message.

WARNING: The message of an exception that a tool throws is sent to the model, and may be shown to the user. Do not put secrets or internal details in it. This includes the exceptions that the tool does not create, such as those of HTTP clients, database drivers or parsers, whose message may contain internal host names, queries or text from an upstream response. Catch them and throw an exception with a fixed message, or map them with an `McpErrorExceptionMapper`.

Arguments that cannot be bound or fail bean validation are tool execution errors too, with the message of the error, for example `date: must be a date in the past or in the present`. They are logged at `DEBUG` level.

An exception that a bean implementing `io.micronaut.mcp.server.exceptions.McpErrorExceptionMapper` maps is answered with a protocol error, with the code and message of the `McpError` the mapper returns. The mappers that Micronaut MCP provides for arguments that cannot be bound or fail validation do not follow this rule: their message is sent as a tool execution error. They are chosen by the type of the exception, not by where it was thrown. The same exception thrown by the tool body itself, for example a `SerdeException` when the tool parses a malformed response, is also sent to the model as an error in its arguments, and is logged at `DEBUG` level. Catch such an exception in the tool and throw another one if that is not wanted.

The exception is looked up after unwrapping the wrappers added by reactive types and `CompletionStage`, so the same mapper and message apply whether the tool throws, returns a failed `Mono` or a failed `CompletableFuture`, and in both execution models.

The other primitives (prompts, resources and completions) answer every failure with a protocol error, using the mapped error when a mapper matches.
